# P2 plan

P1 proved the semantic/runtime architecture and selected a Rust shared portable core. P2 validates actual product-host workflows, starting on macOS.

## P2-A — macOS Capture / OCR / Overlay vertical slice

Status: Active. A1 capability evidence and ADR-008 are recorded, and the minimal macOS host builds. Granted-permission direct-host acceptance is blocked because normal System Settings Add/Open did not register the local app. Authoritative task scope and per-criterion evidence are in `work/current.md`.

User-visible target:

```text
user explicitly triggers capture
→ selects/uses an authorized on-screen source
→ app captures a frame locally
→ local OCR extracts text
→ translation backend processes the text
→ translated result appears in a transient overlay
```

### Stage A1 — capability and requirement evidence

- inspected macOS 26.6.2, Xcode/SDK 27.0, Swift 6.4, and the existing P1-F C ABI
- confirmed ScreenCaptureKit single-window/display selection and one-shot frame capture at the macOS 14.0 deployment target
- confirmed Vision revision 3 supports `zh-Hans` and passed a controlled text/geometry oracle
- type-checked AppKit host and transient non-activating panel configuration
- recorded the capture/OCR/privacy/request-generation contract and implementation limits in ADR-008 and `work/current.md`; the record notes the contract's timing deviation

The selected APIs are based on local SDK probes and host build evidence, not prior convention. The exact source references and alternatives are in ADR-008.

### Stage A2 — architecture and state contract

Record an ADR for:

- capture adapter
- OCR adapter
- translation-backend adapter
- overlay adapter
- request lifecycle/state owner
- permission/error mapping
- own-overlay/self-capture cycle guard
- temporary frame/text memory ownership

Minimum P2-A flow is one-shot, explicit user-triggered capture. Continuous/background capture is a future scope unless current user requirements explicitly change.

The app calls the P1-F Rust `marco-runtime.v1` fixture resolver. Python/MARCO remains the separate reference regression; adding it as an app process dependency would violate FR-021 and the P2-A scope.

### Stage A3 — minimal native macOS app

Implement only the surface required to prove the end-to-end use case:

- app launch
- capture trigger/source selection
- local OCR
- translation handoff
- transient overlay
- cancel/dismiss/retry
- diagnostics needed for validation

Avoid account, settings, updater, telemetry, tray/menu extras, history browser, packaging polish, or generalized UI framework abstractions unless a current acceptance criterion requires them.

The app launch, capture action, cancel/settings controls, and denied-permission guidance were directly observed. The host source and controlled unit checks are listed in `work/current.md`.

### Stage A4 — direct macOS validation

The granted capture/OCR/translation/overlay path, repeated cycle guard, successful network-denied app flow, app-data inventory, and direct latency report are blocked: two normal System Settings Add/Open attempts did not register the running host app. The app is ad hoc signed and this Mac has no valid code-signing identity; the cause is unconfirmed, and signing/distribution remains outside P2-A. Do not mark these complete from component or CLI checks.

Direct host evidence must cover:

- permission denied and granted paths
- real on-screen capture
- controlled OCR fixture
- supported translation fixture
- unknown/unresolved safety
- overlay lifecycle
- self-capture prevention
- cancellation/re-entry
- no default capture persistence
- offline execution
- latency baseline
- P1 regressions
